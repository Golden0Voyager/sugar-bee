# 体成分(体脂率 / 内脏脂肪 / 肌肉量)记录与趋势设计

## 概述

把智能体脂秤**整屏截图**通过现有的「图片上传 → AI 识别」通道录入,除体重外额外保存
8 项体成分数字,并在界面上提供「体成分趋势」视图。

用户最关心三项:**体脂率、内脏脂肪等级、肌肉量**。其余指标一并保存,放在「更多指标」里。

截图样例如下(用户实测,男,体重 70.45 kg):

| 指标 | 示例值 | 单位 |
|------|--------|------|
| 体重(已有字段 `weight`) | 70.45 | kg |
| 体脂率 | 21.7 | % |
| 体脂量 | 15.3 | kg |
| 肌肉量 | 52.3 | kg |
| 骨骼肌量 | 27.0 | kg |
| 蛋白量 | 13.8 | kg |
| 内脏脂肪等级 | 9 | 级 |
| 基础代谢 | 1562 | kcal |

BMI 不来自截图,继续由本系统用 `user_profiles.height` 计算(现有 `settings.calculate_bmi`)。

## 目标

- 一张秤面截图,AI 一次识别出上述全部数字,写进同一条「体重记录」。
- 三项核心指标在「体重管理」面板内一眼可见,并给出**由本系统计算**的状态(标准 / 偏高 / 偏低)。
- 提供独立的「体成分趋势」面板,可切换查看体脂率 / 内脏脂肪 / 肌肉量三条曲线。
- 支持时间范围(近 7/14/30/60/90 天 / 全部)与按天前后翻页,口径与「体重趋势」卡一致。

## 非目标(本轮不做)

- 不新增手动录入表单;体成分只走「截图 → AI 识别」这一条路。
- 不做文件/CSV 导入。
- 不改动 MCP 读写工具的接口(reader/writer),本轮不暴露体成分工具。
- 不改动 Garmin 同步(它本来也不导入体重)。
- 不新增底部/顶部导航入口。

## 反目标(即使能跑也算失败)

- 把秤自己显示的「标准 / 偏高」照抄入库或直接展示 —— 状态必须由本系统算。
- 新开一个「体成分」页签,把「体重管理」藏起来或割裂开。
- 把状态文字(如「偏高」)存进数据库。
- 让 8 项指标挤在一行、手机上需要横向滚动。

## 约束

- `records` 表新增列必须**双端都能迁移**。现状:SQLite 侧有 `utils/db.py` 的 `mig_cols`
  ALTER 列表;Postgres 侧(`_init_db_postgres`)只有 `CREATE TABLE IF NOT EXISTS`,**没有**
  records 的 ALTER 通道(全文件仅 line 732 一处 `ALTER TABLE records`,在 SQLite 分支)。
  所以只改 `mig_cols` 对**已存在的线上库无效**,需要补 PG 侧的等价迁移(见「实施要点」)。
- 体成分字段挂在**已有的** `type='体重记录'` 那一行上(该行 `value=0`),不新增记录类型。
- 阈值只在**一处**定义(Python),前端不得复制一份;现有 `AGENTS.md` 已把这条列为 gotcha
  (`getBadgeForRate()` Python/JS 双份的历史教训)。
- 仍要维持仓库的测试门槛:新增 Python 代码需带测试,`fail_under` 不低于现值。
- 手机优先:核心三项在手机上必须一行放下且不横向滚动。

## 已定方案(用户已确认)

### 1. 录入路径

沿用现有「图片上传 → `glucose_parser.parse_health_data` → 结构化记录」通道。
秤面截图作为图片输入,识别结果是一条 `type='体重记录'` 记录,`weight` + 全部体成分字段一起写入。

### 3. 状态(标准 / 偏高 / 偏低)由系统计算

新增在 `settings.py`,与 `get_bmi_category` 同风格,返回 `{'label': str, 'color': str}`:

| 函数 | 输入 |
|------|------|
| `get_body_fat_category(rate, gender, age)` | 体脂率 + 性别 + 年龄 |
| `get_visceral_fat_category(level)` | 内脏脂肪等级 |
| `get_muscle_mass_category(muscle_mass, weight, gender)` | 肌肉量 + 体重 + 性别 |

状态在 `services/dashboard_service.py` 里算好,随 `stats` 传给模板,Jinja 直接渲染。

## 阈值与显示口径(用户已定 + 我的判断)

M1 由用户选定;M2–M10 用户未表态,我按合理默认定,集中标出便于复核。

### M1. 体脂率阈值(按性别 + 年龄段)—— **用户已选定此方案**

采用通行的体成分参考区间,归纳为三档。**男性**:

| 年龄 | 偏低 | 标准 | 偏高 |
|------|------|------|------|
| 18–39 | < 8% | 8–19% | > 19% |
| 40–59 | < 11% | 11–21% | > 21% |
| ≥ 60 | < 13% | 13–24% | > 24% |

**女性**在每档上 +8~10 个百分点(如 18–39:偏低 < 21%、标准 21–32%、偏高 > 32%)。

年龄取 `user_profiles.birth_year`;档案未填时 `DEFAULT_PROFILE` 兜底为 1964 年(≈62 岁),
会稳定落进「≥ 60」档。

> **已知与草图不一致(用户确认接受)**:示例 21.7% 落在「≥60 男」的 13–24% 内,因此界面会显示
> **「标准」**,而早期草图里写的是「偏高」。用户已明确选择按年龄分档,以本表为准。
>
> 因此 `get_body_fat_category(rate, gender, age)` **需要 `age` 形参**。

### M2. 内脏脂肪等级阈值

沿用主流体脂秤(Tanita / Omron)的通用分档:

| 等级 | 状态 |
|------|------|
| 1–9 | 标准 |
| 10–14 | 偏高 |
| ≥ 15 | 高(红色,提示就医咨询) |

### M3. 肌肉量阈值 —— 必须按比例,不能看绝对值

秤上的「肌肉量」包含体内水分,约为 `体重 − 体脂量 − 骨量`,所以 52.3 kg 这个绝对数
换个 60 kg 的人就完全不适用。改用**占比** `肌肉量 ÷ 体重`:

| 男 | 状态 | | 女 | 状态 |
|---|---|---|---|---|
| ≥ 78% | 优秀 | | ≥ 72% | 优秀 |
| 70–78% | 标准 | | 64–72% | 标准 |
| < 70% | 偏低 | | < 64% | 偏低 |

> 交叉验证:示例 52.3 / 70.45 = 74.2% → 「标准」,与草图一致。
> 注意:不同品牌的「肌肉量」定义不同(是否含水、是否含骨),这套阈值是按示例秤的口径定的;
> 换秤可能整体偏移。

### M4. 数据库列名

挂在 `records` 上,类型与现有列风格一致:

| 列名 | 类型 | 含义 |
|------|------|------|
| `body_fat_rate` | REAL | 体脂率 % |
| `body_fat_mass` | REAL | 体脂量 kg |
| `muscle_mass` | REAL | 肌肉量 kg |
| `skeletal_muscle_mass` | REAL | 骨骼肌量 kg |
| `protein_mass` | REAL | 蛋白量 kg |
| `visceral_fat` | REAL | 内脏脂肪等级 |
| `basal_metabolism` | INTEGER | 基础代谢 kcal |

### M5. 趋势卡的数据来源

直接复用前端已有的 `timelineData`(页面注入 + `/api/timeline?days=N` 按需加载)。
`services/timeline_service.build_timeline` 用的是 `SELECT *`,新列会自动出现在返回里,
**无需新增接口**。图表初始化照抄 `initWeightChart(days, offset)` 的写法。

### M6. 「展开」是滚过去还是原地隐藏

所有趋势卡(血糖趋势、体重趋势)都是常驻显示的,数据不足时卡片自隐。所以:
新增的「体成分趋势」卡**常驻**(有体成分数据才显示),「展开查看趋势 ⌄」点击后**滚动**到该卡,
而不是把卡藏在点击后面。

### M7. 截图信息不全时

秤面可能只显示部分指标(不同品牌/型号)。识别的原则是**只写认出来的字段,其余留空**。
展示层:某一项为空则该项色块隐藏;三项核心全空则不显示体成分行与趋势卡。
不做「缺项补 0」。

### M8. 阈值如何到前端(单一来源)+ 「标准线」画哪条

阈值只在 Python 定义,但要画到折线图上。做法照抄现有 `stats.glucose_targets`
(`index.html` 里 `{{ stats.glucose_targets | tojson }}` 的用法):由
`dashboard_service` 把三个指标的阈值一并放进 `stats`,`initBodyCompChart` 直接读。

线的语义**按指标方向区分**(不是所有指标都画「上限」):

| 指标 | 参考线 | 取值 |
|------|--------|------|
| 体脂率 | **上限**虚线(超过即偏高) | 当前用户的性别/年龄档上限 |
| 内脏脂肪 | **上限**虚线 | 常数 9 |
| 肌肉量 | **下限**虚线(低于即偏低) | `占比下限 × 最新体重`,换算成 kg |

> 肌肉量的判定本是比例,图上要画一条 kg 线就必须定一个参照体重;取**最新体重**这一个基准。
> 这是显示层的近似,判定本身仍走比例,不因这条线的位置改变。

### M9. 行与卡的显示口径统一

「体重管理」里的体成分行、以及「体成分趋势」卡,**共用同一个显示条件**:
三项核心(体脂率 / 内脏脂肪 / 肌肉量)中**至少一项有值**才显示。
只有非核心字段(如蛋白量)有值时,两者都**不显示**,避免出现三个页签全空的卡。

### M10. 「更多指标(仅最新值)」的口径

按**逐字段**取最新:每项指标各自最近一次有值的记录(例如蛋白量上次记录是 3 周前,就显示那次的值)。
理由:秤面截图经常不完整,逐字段取能最大化利用已有数据。实现上是一次
`ORDER BY timestamp DESC` 扫描取每列第一个非空值,不新增接口。
若你更想要「只显示最近一条体成分记录里有的字段」,说一声,改 `dashboard_service` 一处即可。

## 实施要点(给实现者)

### 后端

1. `utils/db.py`:
   - SQLite 分支:`mig_cols` 追加 M4 的 7 列。
   - Postgres 分支:`_init_db_postgres` 的 `CREATE TABLE IF NOT EXISTS records` 里追加同样 7 列
     (**只对新库生效**),并**新增**一段对已有库生效的迁移,形如
     `ALTER TABLE records ADD COLUMN IF NOT EXISTS <col> <type>`(`IF NOT EXISTS` 幂等,
     重复启动安全)。这是本轮**必须**补的一段——否则线上库不会出现新列,`SELECT *` 直接报错。
   - `models.py` 的 `records` 定义同步追加 7 列(Alembic 当前 `upgrade()` 为空 `pass`,不是有效通道)。
2. `glucose_parser.py`:
   - 提示词新增「体成分识别规则」:`体重识别规则` 一节旁并列,说明秤面各数字的归属,
     特别强调 **体脂率(%)与体脂量(kg)不是一回事**、**肌肉量与骨骼肌量不是一回事**、
     **内脏脂肪是等级不是百分比**、**基础代谢单位是 kcal**。
   - JSON schema 追加 `body_fat_rate` / `body_fat_mass` / `muscle_mass` / `skeletal_muscle_mass` / `protein_mass` / `visceral_fat` / `basal_metabolism`。
3. `routes/api_records.py`:`/add` 与 `/batch_add` 的取值、INSERT 列与占位符各加 7 项;
   `_validate_record_data` 增加范围警告(体脂率 3–60%、内脏脂肪 1–30、基础代谢 500–4000 kcal 之类)。
   现有「3 分钟内同体重视为重复(409)」保持不变。
4. `settings.py`:新增 M1–M3 三个分类函数。
5. `services/dashboard_service.py`:取出最新一条体成分,算好三个状态,加入 `stats`。
6. `services/timeline_service.py`:无需改(`SELECT *`)。

### 前端(`templates/index.html`)

   放在体重趋势卡之后。
